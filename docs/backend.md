# Backend и HTTP-контракт

## Актуализация: целостность данных, 30 октября 2026

Действующая модель авторизации, изоляции и журналирования описана в [security.md](security.md). Ниже — целостность данных и будущие банковские контракты.

- Сервер возвращает `_revision` в состоянии. `PUT /api/store` требует ту же версию; отсутствующая или устаревшая версия даёт **409 `state_conflict`** без записи. Каждый подтверждённый платёж и сохранение увеличивает версию. Проверка версии и запись выполняются внутри `BEGIN IMMEDIATE`.
- Клиент ждёт ответ PUT до изменения кэша и сообщения об успехе. Повторные нажатия блокируются на время записи. Формы сохраняют исходную версию, чтобы изменения из другой вкладки не превращались в незаметную перезапись. Конфликт показывается постоянным сообщением; автоматического повторного сохранения чужой версии нет. Перед обновлением пользователь может скопировать введённый текст.
- Общий PUT не создаёт платежи или бонусы, не изменяет суммы, получателей уже распределённых чаевых и подтверждённые выводы. Для нового демовывода сервер проверяет доступный баланс. Распределение ожидающих сумм проверяется на целые копейки, сохранение общей суммы и активных получателей.
- `POST /api/payments` требует строковый ID длиной 1–100 символов из ASCII-букв, цифр, `_` и `-`. Усечение исключено. Повтор того же ID и нормализованных параметров тем же гостем в том же заведении возвращает прежний платёж; другие параметры или владелец дают **409**. Порядок получателей значим для оставшейся копейки. Отпечаток запроса хранится в `tenant_payment_requests` с ключом `(tenant, id)`; для старых операций сравнивается сохранённое содержимое. Старые операции без владельца не становятся публичной гостевой историей.
- Alfa ID остаётся имитацией с любым шестизначным кодом. Запрос кода создаёт запись `alfa_challenges` на 5 минут. Подтверждение требует `phone`, `code`, `challengeId`; запрос привязан к телефону и расходуется один раз транзакционно. Сессия действует 1 час, ответ содержит `expiresAt` в Unix-секундах. При 401 клиент направляет на повторный вход, сохраняя ID черновика.
- На входе проверяются структура данных, вложенные записи, типы чисел, суммы, даты, дубли ID, доли, профили и бонусы. Ошибки возвращаются как JSON 400; ошибки SQLite — 503. `GET /api/health` выполняет запрос к таблице состояния и больше не раскрывает путь к файлу БД.
- Соединения SQLite закрываются после каждого запроса. `backend/backup.py` создаёт согласованную копию через SQLite backup API, включая WAL, и выполняет `integrity_check`.

### Совместимость и границы

`setup()` добавляет столбец `revision` к существующей таблице, столбец `expires_at` к сессиям и новые таблицы. Данные заведения и история сохраняются. Старые демо-сессии без срока действия истекают: потребуется войти заново. Открытые старые версии клиента нужно обновить, поскольку PUT без `_revision` отклоняется. После неоднозначного сетевого сбоя сначала перечитайте данные: сервер мог завершить запись до разрыва соединения.

Заведения и учётные записи менеджеров создаются только административной командой `backend.manage`. Публичная инициализация закрыта. API проверяет роль и заведение сессии; гость получает отдельную проекцию и собственную историю. Аудит фиксирует изменения транзакционно. Общий PUT пока не обеспечивает отдельную идемпотентную квитанцию вывода при потере ответа; выделенные команды остаются следующим этапом.

### Проверка

`python -m unittest discover -s backend -t .` запускает модели, HTTP-контракты, конкурентные платежи/сохранения/выводы, миграцию и резервное копирование. CI и Docker используют эту же команду. Клиентские тесты `npm test` дополнительно проверяют ожидание подтверждения, 409, отказ сети, невозможность скрытой локальной оплаты после обнаружения API и восстановление входа.

В репозитории реализован демонстрационный backend `backend/server.py`. Это dependency-free Python-сервис с SQLite, который запускается вторым контейнером в `docker compose`. Nginx публикует его по тому же origin на `/api`, поэтому браузеру не нужны CORS-разрешения и отдельный адрес API.

Реализованные маршруты:

- `GET /api/health` — проверка доступности SQLite без раскрытия пути;
- `GET` / `PUT /api/store` — состояние, доступное роли персонала в её заведении;
- `GET /api/guest/store` — публичные данные и собственная история гостя;
- `POST /api/store/initialize` — совместимый ответ уже существующего состояния менеджеру, без публичного создания базы;
- `GET /api/venue` — публичные данные заведения и активных получателей;
- `POST /api/payments` — атомарное создание чаевых; повторный `Draft.id` возвращает уже созданную операцию;
- `GET /api/payments/:id` — подтверждённая демо-операция;
- `POST /api/auth/alfa-id/request` — создаёт демо challenge для номера;
- `POST /api/auth/alfa-id/verify` — принимает шестизначный демо-код и выпускает случайный локальный токен.

Сервер проверяет границы суммы, активность получателей, повторы ID, рейтинг, допустимый метод оплаты и рассчитывает равные доли и апельсинки самостоятельно. SQLite использует WAL и `BEGIN IMMEDIATE` при создании платежа, поэтому два одновременных запроса с одинаковым ID не создадут две операции.

Это не банковский backend: код не отправляет SMS, не принимает полные карточные реквизиты, не списывает деньги и не использует реальный Alfa ID. Доступ, аудит и проверка версии реализованы; для production нужны платёжная интеграция, нормализованный денежный реестр и отдельная эксплуатационная проверка.

## Граница интеграции с сервером

Названия сущностей соответствуют слоям исходной Archi-модели: заведение, сотрудники, экран чаевых, платёжный шлюз, история чаевых, настройки пользователя, кабинет заведения.

Целевой production-контракт (частично реализован упрощённым демо-сервисом):

- `GET /api/venues/:id` — название, адрес, сумма счёта из POS, доступные сотрудники, комиссия, правило распределения. В демо `Store.venue`, `Store.employees`, `Store.settings`.
- `POST /api/payments` — сумма в копейках, получатели/доли, метод, оценка/теги/текст, `idempotencyKey`. Сервер проверяет доступность получателей, лимиты и сумму долей и возвращает платёжный ID и URL шлюза.
- `GET /api/payments/:id` — состояние pending/succeeded/failed. Сервер подтверждает платёж по подписанному webhook эквайринга. Клиентское подтверждение не является основанием зачисления.
- `GET /api/employees/me/tips` и `GET /api/employees/me/balance` — суммы, отзывы и подтверждённые зачисления сотруднику.
- `PATCH /api/employees/me` — описание, имя, цель, уведомления.
- `POST /api/payouts` — идемпотентная заявка на вывод; реквизиты токенизируются банковским провайдером.
- `GET /api/venues/:id/tips` — фильтры по периоду, сотруднику и статусу, серверная пагинация.
- `GET /api/venues/:id/reviews`, `PATCH /api/reviews/:id` — отзывы и отметки прочитанного.
- `POST /api/venues/:id/employees`, `PATCH /api/employees/:id` — создание/пауза сотрудников.
- `PATCH /api/venues/:id` — настройка реквизитов заведения и долей.
- `POST /api/venues/:id/distributions` — атомарное распределение нераспределённых сумм. Повторные запросы не должны распределять одну операцию повторно.

В production сервер должен обеспечивать авторизацию и изоляцию ролей/заведений, авторитетную проверку сумм/комиссий, транзакции баланса, блокировки или optimistic concurrency и идемпотентность, проверку webhook, аудит, срок хранения отзывов, обработку ошибок и повторов. `localStorage` прототипа не является учётной системой, платёжным реестром или защитой ролей. На нескольких устройствах/при конкурентных платежах используется серверная транзакция.

Фронтенд использует `src/repository.ts` как адаптер. До показа рабочих данных он загружает соответствующую проекцию API; при отказе сервера показывает ошибку. Кэш разделён по заведению и пользователю, черновик — по заведению. Оплата и сохранение не переходят в локальную имитацию. Повторное нажатие во время записи блокируется; ошибки и конфликты видны в постоянном уведомлении.


## Согласованный сценарий оплаты и состав команды

Заказ оплачивается первым. Затем гость оставляет чаевые в том же интерфейсе; это отдельная подтверждаемая операция. Общая страница используется в приложении Альфы, веб-версии и по напоминанию. Реальная интеграция с приложением банка и наследование источника оплаты пока не реализованы; способы оплаты в текущем макете демонстрационные.

Сервер отдаёт массив `employees`: стабильный `id`, `name`, `role`, `active`, `photo`, `goal`, `bio`. Роль — текст для отображения, а не ключ получателя; допустимы несколько поваров или совмещённая роль. Количество активных сотрудников определяет число карточек и долей. Список берётся из `Store.employees` через адаптер `repository.ts` и синхронизируется с HTTP-сервером при его подключении.

`Draft.recipientIds` и `Store.settings.recipientIds` связывают доли с идентификаторами людей. Перестановка сотрудников не меняет распределение. При изменении состава в форме возвращаются равные доли; уже подтверждённая история сохраняется. Перед отправкой сервер повторно проверяет получателей. Оставшийся `coreIds` в модели обслуживает исходные демоданные и совместимость старых черновиков, интерфейс от него не зависит.

Режим `splitMode` отделён от чисел. Открытие «Свои доли» сохраняет точное равное распределение, поля показывают округлённые целые проценты. При редактировании разрешены только целые значения от 0 до 100; остаток рассчитывается автоматически, сумма долей сохраняется равной 100%. В равном режиме суммы на карточках приблизительные при наличии остатка и отмечены «≈»; подтверждение и история используют фактические копейки. Вся сумма распределяется получателям.
