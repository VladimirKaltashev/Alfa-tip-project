## Повторная ревизия: данные, API и эксплуатация

Приоритет — целостность данных учебного прототипа. Каждая задача проверяется отдельно; внешний вид, авторизация и реальная банковская интеграция не считаются решёнными наличием API.

1. Версия серверного состояния с миграцией существующей SQLite.
2. Ответ 409 на сохранение устаревшего состояния.
3. Сохранение в интерфейсе только после подтверждения сервера.
4. Защита от повторного нажатия во время сохранения.
5. Видимое сообщение о конфликте без автоматической перезаписи чужих изменений.
6. Запрет добавления платежей и бонусов через общий PUT.
7. Проверка получателей при распределении старых сумм.
8. Проверка демовыводов по серверному балансу, защита от перерасхода.
9. Строгие ID платежей без усечения.
10. Проверка несовпадающих параметров при повторе ID платежа.
11. Хранение одноразовых запросов Alfa ID, срок действия и привязка к номеру.
12. Ограниченный срок жизни демо-сессий и обработка истечения в клиенте.
13. Проверка формы JSON и вложенных сущностей до записи.
14. Проверка БД в healthcheck без раскрытия пути к файлу.
15. HTTP-тесты контрактов, ошибок и конкурентных запросов.
16. Клиентские тесты поведения при 409, ошибках сети и успешном сохранении.
17. Документация запуска, миграции, восстановления после конфликта и ограничений.
18. Сборка и полный прогон проверок после интеграции.

Отдельные этапы, требующие дальнейшего проектирования: роли и изоляция заведений, замена общего PUT специализированными командами, резервное копирование и восстановление БД, постраничная история, лимиты запросов, аудит действий, интеграционные секреты, доступность интерфейса и браузерные сценарии. Реальные платежи требуют договора и API банка. Подделка денежных данных через API должна быть закрыта независимо от будущей авторизации.

## Соответствие критериям

SQLite, HTTP API, React и сторонние библиотеки уже присутствуют (C2: сложность). Workflow тестирования, контейнеризации и условного деплоя уже есть; его наличие не доказывает успешный деплой. Дедлайны оцениваются по истории команды, из кода их установить нельзя. Обоснование стека есть в README. Скриншоты банка используются как визуальные референсы, а новая вложенность — проектное предложение, не утверждение о реальном расположении сервиса в приложении банка.
