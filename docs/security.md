# Доступ, изоляция и аудит — 30 октября 2026

## Действующая модель

| Роль | Доступ |
| --- | --- |
| Гость | Публичные данные кафе, активные получатели без карточных реквизитов, собственные платежи и бонусы по гостевой cookie |
| Сотрудник | Только свой профиль, свои доли чаевых и выводы; изменение имени, описания, цели, последних четырёх цифр карты и уведомлений |
| Менеджер | Данные своего заведения, команда, статистика, распределение, отзывы, создание/отключение доступов сотрудников и журнал; вывод чужих средств запрещён |
| Администратор сервера | Создание заведений и менеджеров, восстановление пароля через CLI; публичной регистрации нет |

Авторизация проверяется на сервере для каждого запроса. Демо Alfa ID не выдаёт права персонала. Клиентское поле роли, изменение URL или localStorage не дают доступ к чужому кабинету.

## Сессии

Персонал входит по логину и паролю. Хранится PBKDF2-SHA256 с индивидуальной солью и 600 000 итераций, не исходный пароль. Вход ограничен десятью неудачными попытками в минуту на сочетание адреса соединения и заведения; за reverse proxy это общий лимит для его адреса. Не считайте его полноценной защитой от распределённой атаки.

Случайная cookie `alfa_staff` имеет `HttpOnly`, `SameSite=Strict`, `Path=/api`, срок 8 часов. В базе хранится её SHA-256-отпечаток. Выход, отзыв доступа и восстановление пароля отзывают сессии. Интерфейс проверяет сессию при возвращении в окно и раз в минуту; API проверяет её на каждом запросе. Кабинетный кэш находится в sessionStorage под ключом пользователя и заведения и очищается при выходе.

Гостевая cookie `alfa_guest` действует 30 дней и определяет владельца истории. Это анонимная история браузера, а не личный кабинет банка и не восстановление по номеру телефона. После удаления/истечения cookie гостевая история недоступна; зачисления в заведении сохраняются. Бонусы разных гостей не смешиваются. Успешный повтор чужого ID платежа не раскрывает чужую операцию.

Для HTTPS-развёртывания установите `ALFA_COOKIE_SECURE=1` и завершайте TLS на доверенном reverse proxy. Значение 0 предназначено для локального HTTP. Запись требует `application/json`; запросы с Origin другого сайта отклоняются. Nginx сохраняет исходный Host. CORS-доступ к API не предоставляется.

## Заведения и миграция

Заведение выбирается параметром страницы `?venue=<id>`. Клиент передаёт `X-Venue-ID`. Для персонала сервер обязательно сверяет его с заведением учётной записи. Идентификатор состояния SQLite — `application_state.state_key`; ключи идемпотентности и владельцы платежей включают ID заведения. Кэш и черновики браузера тоже разделены по заведению. QR и отложенные ссылки несут ID заведения.

Старая запись `demo` сохраняется без сброса истории. Для доступа к ней администратор создаёт менеджера командой `create-user`. Старые операции без владельца не присваиваются первому гостю: они остаются видны менеджеру и соответствующим сотрудникам. Старые глобальные кэши не используются. Они не импортируются автоматически в новую защищённую базу.

Пустая база больше не инициализируется первым браузером. `POST /api/store/initialize` оставлен только для совместимости: требует менеджера и возвращает уже существующее состояние. Создание нового заведения выполняется через CLI.

## HTTP-контракт доступа

| Маршрут | Назначение |
| --- | --- |
| `POST /api/auth/login` | `{username,password}`, выдаёт staff cookie |
| `GET /api/auth/session` | ID, роль, заведение, сотрудник и срок текущей сессии |
| `POST /api/auth/logout` | Отзывает текущую сессию и удаляет cookie |
| `GET /api/store` | Полное состояние менеджеру, ограниченная проекция сотруднику; анонимному клиенту 401 |
| `PUT /api/store` | Проверяет роль, поля, `_revision` и денежные инварианты; при конфликте 409 |
| `GET /api/guest/store` | Только публичные данные и история текущего гостя |
| `GET /api/venue` | Публичная карточка кафе и активные получатели без карточных реквизитов |
| `POST /api/payments` | Демо-платёж из `{draft}`, без клиентской базы; результат содержит гостевую проекцию |
| `GET /api/payments/:id` | Только операция текущего гостя; чужая/отсутствующая — 404 |
| `GET /api/team/accounts` | Менеджеру: логины, привязки к сотрудникам и статус доступа |
| `POST /api/team/accounts` | Менеджеру: `{username,password,employeeId}`; только роль employee |
| `POST /api/team/accounts/revoke` | Менеджеру: `{id}`, отключение employee своего заведения и отзыв сессий |
| `GET /api/audit?before=<id>&action=<action>&role=<role>` | Менеджеру: 50 событий своего заведения, фильтры применяются до пагинации, `nextBefore` для следующей страницы |

## Аудит

Записываются успешные/неуспешные входы, выходы, изменения состояния, платежи, выводы, создание и отзыв доступов, административные операции. Денежное событие и изменение состояния фиксируются в одной транзакции; повтор успешного платежа не добавляет событие повторно. В журнале — идентификатор автора, роль, заведение, время UTC, тип действия, объект и краткие метаданные. Пароли, cookie, токены и тексты отзывов не записываются.

API не предоставляет редактирование или удаление аудита; SQLite-триггеры запрещают UPDATE/DELETE. Это защита от изменения через приложение, а не криптографически независимый журнал: владелец файла БД может изменить схему. Для production нужны внешний журнал, правила хранения и мониторинг.

## Оставшиеся границы

Реальные платежи, выплаты, SMS и банковский Alfa ID не подключены. Нет MFA, самостоятельного восстановления пароля, отдельной квитанции идемпотентности вывода, внешнего аудита и нагрузочной проверки. Данные ещё хранятся JSON-состояниями заведений, а не нормализованным денежным реестром. SQLite backup работает для всей базы; изоляция API не означает физически отдельные файлы БД.

Визуальная проверка не подтверждена: запрос доступа к Chrome повторно истёк. Серверные тесты покрывают права и изоляцию, но не заменяют проверку интерфейса, внешний аудит безопасности и проверку целевого развёртывания.
