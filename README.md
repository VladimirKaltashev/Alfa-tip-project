## Запуск

Нужен Node.js 22.6+ (проверено на Node.js 26).

```sh
npm ci
npm run dev
```

Теперь требуется backend: Vite направляет `/api` на `127.0.0.1:8000`. Сначала запустите backend и создайте заведение/менеджера по инструкции [DEPLOY.md](DEPLOY.md). Пользователей и паролей по умолчанию нет. При недоступном API приложение показывает ошибку, а не имитирует успешное действие локально.

Открыть http://localhost:5173. С телефона в той же Wi-Fi сети: `http://<IP-компьютера>:5173`. QR-код использует текущий адрес страницы: для сканирования телефоном открывайте кабинет через сетевой IP, а не localhost.

```sh
npm run build
npm test
npm run preview -- --port 4173
```

## Демонстрационные данные

Оплата и вывод имитируются, без банковских SDK и полных реквизитов. Доступ к кабинетам персонала требует учётной записи и проверяется сервером. Название, адрес и счёт редактирует менеджер своего заведения. Комиссия 0 ₽ задана только для демо, не является тарифом банка.

Источник данных — SQLite через API. Кэш персонала хранится в sessionStorage с ID пользователя и заведения; гостевой кэш и черновик — в localStorage с ID заведения. История гостя ограничена его HttpOnly-cookie, сотрудника — его профилем, менеджера — его заведением. Локального резервного режима оплаты и сохранения больше нет.

Начальный состав: Александр (официант), Мария (повар), Максим (бармен). Количество сотрудников и роли не фиксированы: индивидуальные чаевые и разделение доступны для активных сотрудников из данных. При изменении состава предлагаются равные доли. Все суммы хранятся целыми копейками. Остаток округления распределяется по наибольшей дробной части; сумма сохраняется.

## Backend

`backend/server.py` — встроенный dependency-free Python API с SQLite. В Docker Compose он запускается рядом с Nginx и доступен только через reverse proxy `/api`. `src/repository.ts` — адаптер данных: загрузка состояния, синхронизация изменений, Alfa ID и идемпотентное создание демо-платежа. Контракт, схема данных и ограничения описаны в [docs/backend.md](docs/backend.md).

Реализованы SQLite, атомарное демо-зачисление, роли персонала, изоляция заведений, гостевые сессии и аудит. Реальные платежи/выплаты, SMS/push, CRM/касса и банковский Alfa ID требуют отдельных интеграций. Авторизация персонала независима от демо Alfa ID.

## Обновлённая страница гостя

Сверху — короткая строка заведения и адрес. Затем сумма → разделение → получатели → отзыв → способ оплаты. На всех экранах убран переключатель ролей: кабинеты открываются по своим адресам. После оплаты гость остаётся в своём интерфейсе.

Новый черновик по умолчанию делится поровну между активными сотрудниками; сумма чаевых не выбирается автоматически. В «Свои доли» проценты отображаются целыми. После ввода, например, 70% и 10% оставшаяся доля автоматически становится 20%. При выключении разделения выбирается первый активный сотрудник. В равном режиме округлённые суммы отмечены знаком «≈», а фактическое распределение сохраняет каждую копейку.

Старые неоплаченные черновики один раз переводятся на новый вариант распределения, сохраняя ID, сумму и отзыв. Последующий выбор пользователя сохраняется.

Ссылка «Оставить позже» сохраняет дату визита и сумму демонстрационного счёта в параметрах ссылки (`mode=later`, `visitAt`, `bill`). В таком сценарии под названием места появляется одна дополнительная строка. Контекст сохраняется при переходе к оплате и обратно. В боевом приложении эти данные нужно получать по ID чека с сервера, а не доверять URL.

## Alfa ID, способы оплаты и апельсинки

На странице гостя есть три отдельно оформленных способа оплаты:

- **СБП** — в боевом сценарии открывает приложение выбранного банка;
- **Alfa Pay** — требует демонстрационный вход через Alfa ID и даёт двойные бонусы;
- **Карта** — демонстрационная карта без ввода реквизитов.

`/alfa-id` — имитация Alfa ID. Сервер проверяет одноразовый запрос, номер и шестизначный демо-код; SMS не отправляется и внешний Alfa ID не вызывается. Любой шестизначный код подходит только для демонстрации оплаты, но не для входа в кабинет персонала.

«Апельсинки» — внутренняя демо-механика благодарностей, а не банковская программа и не деньги. За каждые полные 100 ₽ чаевых начисляется 1 апельсинка; при Alfa Pay — 2. Начисление записывается один раз вместе с операцией и не дублируется при повторном подтверждении платежа. Баланс и история находятся на `/rewards`.

`/help` описывает все действия гостя, ограничения демо и различия между СБП, Alfa Pay и картой.

## Технические решения

React выбран для изолированных экранов и управляемого состояния сложной формы; TypeScript — для денежных типов, миграций хранилища и безопасной работы с маршрутами; Vite — для быстрой локальной разработки и статической production-сборки. `lucide-react` даёт единый набор доступных SVG-иконок, а `qrcode` создаёт QR-коды без внешнего сервиса.

Денежные значения хранятся целыми копейками, расчёт долей сохраняет каждую копейку, а создание платежей идемпотентно по сочетанию заведения и ID черновика. SQLite использует транзакции. Роли и сессии персонала реализованы; подключение эквайринга, выплат и банковской идентификации остаётся отдельной задачей.

## CI

Workflow [`.github/workflows/ci.yml`](.github/workflows/ci.yml) на каждом pull request и push в `main` выполняет `npm ci`, проверку форматирования, модульные тесты и production-сборку. Затем собирает и запускает оба контейнера, ждёт healthcheck и проверяет frontend, API через nginx и отказ анонимному клиенту в доступе к кабинету. Временные контейнеры и данные удаляются после проверки. Деплой описан в [DEPLOY.md](DEPLOY.md); наличие workflow само по себе не подтверждает успешную выкладку.

Единый стиль TypeScript, TSX и CSS задаёт Prettier: `npm run format` исправляет оформление, `npm run format:check` проверяет его без записи. `.editorconfig` задаёт UTF-8 и отступы, включая четыре пробела для Python. Форматирование не заменяет архитектурный обзор и тесты. Для локального Docker можно изменить порт через `ALFA_HTTP_PORT` (по умолчанию 80).

Для автоматической выкладки на сервер добавьте в Secrets репозитория `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY` и `DEPLOY_PATH`. Тогда после успешного pipeline в `main` workflow подключится к указанной папке сервера, сделает безопасный `git pull --ff-only` и `docker compose up -d --build`. Пока секретов нет, deploy-job пропускается — никуда не подключается и не передаёт данные.
